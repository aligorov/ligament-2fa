# Анализ лицензирования: векторы копирования и 5 вариантов защиты

Дата: 2026-09-12 · Контекст: HEAD 9b9328e, v0.4.70 · READ-ONLY анализ, код не менялся

## Почему текущую модель легко копировать

Текущая схема: Ed25519-файл, canonical JSON, офлайн-валидация, планы
free (5 юзеров) / demo (≤30 д) / subscription (≤13 мес) / perpetual,
CRL, гейт build-date для maintenance. Конкретные дыры:

1. **Нет привязки к инсталляции.** Один лицензионный файл работает на
   любом числе серверов: купил подписку на 50 юзеров — раздал .pem на
   20 инсталляций (дочкам/друзьям/продал). Технической проверки «этот
   файл для ЭТОГО сервера» нет.
2. **install_id нет вовсе** (grep по internal/license пуст), а любой
   идентификатор в БД копируется вместе с бэкапом — фиксировать надо
   не только в БД.
3. **Free-5 навсегда** — легальный способ жить без оплаты: режь юзеров
   по инсталляциям (3 инсталляции × 5 юзеров = 15 бесплатно).
4. **Demo по одному файлу на всех**: demo-лицензия валидна на любой
   инсталляции — партнёр/клиент раздаёт демки.
5. **Копирование артефактов**: образ Docker Hub публичный;licence
   gate — единственный барьер, и он офлайн.
6. Юридический барьер (лицензионный договор) — единственная реальная
   защита после пересборки бинарника владельцем.

Оценка: модель защищает от честного клиента с ограничениями, но не
защищает от копирования вообще. Ниже 5 вариантов — от дешёвого к
жёсткому; лучшая практика для self-hosted продукта — их комбинация.

## Вариант 1. Привязка лицензии к инсталляции (install binding)

**Суть.** Инсталляция при первом старте генерирует необратимый
код активации = HMAC(master_key, машина-факты) + случайная соль,
показывает его в админке. Клиент присылает код вендору (email/бот).
Вендор выпускает лицензию с полем `install_code_hash` (Ed25519-подпись
этого кода). Сервер принимает файл только если hash совпал со своим
кодом. Смена сервера = перевыпуск лицензии вендором (ручной процесс,
дружелюбный: самодаверка «сборка переехала» 1 раз).

- Защита: ★★★★☆ — файл бесполезен на чужой инсталляции.
- Внедрение: **низкое** (1-2 дня): поле в payload, fingerprint-функция,
  форма в админке, флаг licgen.
- Минусы: ручная активация (поддержка); соль в БД копируется бэкапом —
  код строить от master_key (он в БД!) → дополнить внешним фактором
  (machine-id хоста, см. вариант 4), иначе бэкап+restore на другом
  сервере «переедет» вместе с лицензией.
- Совместимость: офлайн полностью, phone-home не нужен.

## Вариант 2. Онлайн-сверка с сервером вендора (phone-home)

**Суть.** Уже спроектировано ранее (lic-online, отчёт 2026-09-06):
`check_url` в payload, POST {lic_id, customer, install_id} → ответ
canonical JSON {mode: valid|expired|revoked, users, until}, подписанный
Ed25519 вендора; периодичность 1 ч; grace: офлайн-подписка 7 суток,
демо 48 ч → деградация в Free. Вендор-сервер (licgen -serve) видит все
инсталляции в реальном времени: копирование обнаруживается мгновенно
(один lic_id с двух IP).

- Защита: ★★★★★ — единственная схема с гарантией против копирования и
  с дистанционным отзывом.
- Внедрение: **среднее** (5-8 дней): сервер вендора, клиентский тикер,
  grace-логика, статус-страница в админке.
- Минусы: требует выход инсталляции в интернет к вендору (закрытые
  контуры — не подходит, поэтому только для subscription-плана);
  вендорский сервер становится точкой отказа (grace смягчает);
  ранее этот вариант дважды откладывался — возвращать осознанно.
- Рекомендация: включать ТОЛЬКО в payload подписок, perpetual/demo —
  офлайн-схемы.

## Вариант 3. Редакции по фичам (feature-gated editions) вместо одного лимита юзеров

**Суть.** В payload добавляется `features: []`: например `sso`
(OIDC-провайдер), `support` (SOS-консоль), `radius_trust` (окно
доверия), `whitelabel`, `cp` (Windows CP-эндпоинты), `ldap`. Free =
ядро (логин+push+TOTP+RADIUS без trust). Сtility-копирование теряет
смысл: бесплатная сборка без фич — это демо продукта, а купленная
лицензия (в сочетании с вариантом 1) включает фичи только на своей
инсталляции.

- Защита: ★★★☆☆ (сам по себе не останавливает копию, но резко снижает
  ценность копии + создаёт ступени апсейла).
- Внедрение: **низкое-среднее** (2-3 дня): фиче-флаги в Status,
  гейты в роутере/фичах, карточка «Редакция» в админке, licgen-флаг.
- Минусы: дробление продукта; нужно выбрать состав редакций
  (предложение: Starter / Business / Service Provider).
- Бонус: white-label и SOS-консоль становятся платными фичами
  Service-редакции — прямой монетизатор ниши из презентации.

## Вариант 4. Аппаратно-средовой отпечаток (hardware fingerprint)

**Суть.** При установке собирается вектор признаков хоста:
machine-id (/etc/machine-id), UUID материнки/VM (dmidecode/SMBIOS),
hostname, кол-во CPU/RAM-класс. Отпечаток = HMAC(master_key, вектор) с
допуском: лицензия считается валидной при совпадении ≥N/5 компонентов
(переезд VM/апгрейд RAM не роняет). Отпечаток показывается в админке
как код активации → тот же ручной активационный цикл, что в варианте 1,
но код УСТОЙЧИВ к копированию бэкапа (machine-id не в БД).

- Защита: ★★★★☆ (усиливает вариант 1 до «бэкап не переносит лицензию»).
- Внедрение: **низкое-среднее** (2-3 дня): сборщик вектора
  (Linux: /etc/machine-id + sysfs; Docker: монтировать host-факты),
  tolerant-сравнение.
- Минусы: Docker-контейнер по умолчанию не видит host-факты — нужен
  mount/arg в compose (обновить docker-compose.client.yml); виртуалки
  с клонированием диска дают одинаковый machine-id (приемлемо: клон =
  копия инсталляции, что и блокируем).

## Вариант 5. Персональная сборка под клиента (watermarked builds)

**Суть.** Каждый клиент получает СВОЙ Docker-образ: в бинарник при
сборке вшивается невидимый маркер `-X main.BuildCustomer=<client-id>`
(+ та же строка, разбитая, в audit-события). Утечка сборки
идентифицируется по поведению/дампу. В сочетании с вариантом 2 —
сервер сверки сразу видит, чья сборка ходит к нему.

- Защита: ★★★☆☆ (не предотвращает, а атрибутирует: работает на
  юридическую часть и против «слива в паблик»).
- Внедрение: **минимальное** (день): ldflags-параметр в Makefile/
  docker.yml, реестр «клиент → digest» у вендора.
- Минусы: ломает единый публичный образ на Docker Hub → перейти на
  «публичный free-образ + персональные образы платным клиентам»
  (registry vnd.ligam); чуть больше логистики релизов.

## Рекомендуемая связка (приоритет внедрения)

| Этап | Что | Закрывает | Стоимость |
|---|---|---|---|
| 1 | **В1+В4** install binding на machine-fingerprint | копирование .pem и бэкапов | 3-4 дня |
| 2 | **В3** фиче-редакции Starter/Business/SP | «жизнь на free» по кусочкам, апсейл | 2-3 дня |
| 3 | **В5** watermarked образы платным клиентам | атрибуция утечек | 1 день |
| 4 | **В2** phone-home только для subscription | реальные копии подписок, удалённый CRL | 5-8 дней |

Free-5 оставить как есть (это маркетинг), но: Free не получает
`support`, `whitelabel`, `radius_trust` (вариант 3) — уже не «то же
самое, но без лимита», а осмысленно урезанная редакция.

## Что сознательно НЕ делать

- DRM-обфускацию бинарника (self-hosted всё равно пересобирается
  владельцем — legal, not technical).
- Жёсткий отказ старта без лицензии (сейчас login никогда не
  блокируется — сохранить: это защита репутации при сбоях).
- Требование phone-home для perpetual/демо — закрытые контуры.

Реализация — по команде; предлагаю начать с этапа 1 (В1+В4) в одной
волне с миграцией лицензионного payload (обратно-совместимо: файлы
без install_code_hash продолжают работать для уже выпущенных лицензий).
